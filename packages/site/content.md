# bridge

**The outer loop that cajoles your agents & humans**

Your agents run the inner loop: prompt, edit, test, repeat. bridge is the outer loop around them. It decides what work happens next, hands each unit to a fresh agent session, tracks live progress with completion, confidence, and risk, verifies results with an independent session, and routes sign-off to a human when it matters.

It is not a kanban tool and not an agent framework. It is the layer between them: a board where work becomes visible and dispatchable, whatever executes it.

## Install

```bash
curl -fsSL https://raw.githubusercontent.com/state-vector/bridge/main/install.sh | bash
bridge pair https://hub.fleetbridge.run
```

That pairs with the shared hub — the same host you sign in to with GitHub (`https://hub.fleetbridge.run/login`). Self-hosting instead? Deploy your own hub per the README and pair `https://your-hub.workers.dev`.

That is the whole runner. It pairs with your hub using a device code, then claims tasks and dispatches them to `opencode` sessions on your machine, in isolated git worktrees (auto-provisioned per task; teardown preserves uncommitted work to a `wip/` branch and is eventual — terminal tasks sweep at once, everything else no running session holds sweeps after 7 days, BR#3633; the sweep also enumerates `git worktree list` of the runner's clones, and a machine-local **worktree registry** — `~/.bridge/worktree-registry.jsonl`, 2026-11-02 — closes the loop mechanically: the runner registers every provisioned tree at creation and deregisters at teardown, the takeover prompts direct local sessions to register theirs with an exact one-liner (an unregistered tree is never swept — registration IS the contract), and the sweep enumerates registered paths wherever they live, pruning dead lines on read), one PR per task. Results come back to the board for review. Pairing vends a device credential exactly once (hub-generated, stored at `~/.bridge/principal`, never regenerated); re-pairing rotates the gateway token in place against that credential — the hostname is a display label only.

**Git identity is a first-class property of dispatched sessions** (BR#3185): the runner provisions each worktree's repo-local git config from an identity profile — an explicit `identity` block in the config wins, otherwise the built-in `worker` class applies (commits as `detached-cody`, signed with the sv-agents-signing key per the BR#3181 ruling). Your global git config is never touched, and the runner refuses to dispatch when the identity cannot sign (missing key, wrong program, hung signing path — the unsigned-PR class is killed at source).

**Token rotation is graceful and self-healing** (BR#3787): tokens rotate in place against the device's principal — but a rotation never amputates. Identity is anchored by the **principal only** (a label held by another device's credential is refused or suffixed, never stolen — the 2026-10-27 fleet 401 ping-pong was label theft); the **previous hash keeps authenticating for 72 hours** (flagged stale) so in-flight dispatches finish; every response carries the token's **epoch**, and the runner re-vends its own row **proactively** (`/api/token/repair` on the agent plane — the principal is the credential, so headless gateways self-heal with no human session, rate-limited 6/hour). Every repair failure reason is logged, never swallowed.

**Identity rendering: owner columns show labels, principals stay invisible** (BR#4262): the owner stored on a card is the principal (the anchor every match keys on); every display surface — board, orient, card reads, my-tasks — resolves it through a render-time join to the owning token's **label**, falling back to the stored value verbatim for legacy owners (`system:*`, hand-minted labels) with no token row. New principals are vended `dev_`-shaped so an anchor can never be mistaken for a `bkw_` token, and every label door (`token.rename`, pair approve, `agent.provision`, human mint) rejects `bkw_`/`dev_`-prefixed labels — a token-shaped label once rendered a raw credential into owner columns. **Machine/agent names are display, not identity** (2026-10-29): a hostname change (macOS local-name rotation, network `-2` suffixes, a VPS's DHCP IP) used to mint a fresh gateway identity — and, because agent labels are namespaced `<gateway>/<agent>`, a fresh identity per provisioned agent — piling dead labels on the board. Renames through the principal anchor now record the old name in `identity_aliases` and resolve everywhere: provisioning under a renamed gateway renames the agent token **in place** (same id, same stored secret), the identity list collapses each machine/agent to its live label with retired names shown as aliases, and `admin.alias {alias, canonical}` merges the legacy labels that predate the anchor.

Every push to `main` also publishes a rolling **dev** pre-release of the binaries — `install.sh` with no arguments always resolves to the newest versioned release, never dev. Install the dev channel with `curl -fsSL https://raw.githubusercontent.com/state-vector/bridge/main/install.sh | bash -s -- dev`.

## Three surfaces, one hub

- **Gateway**: desktop app and the headless `bridge` CLI: auth, a live dispatch log, agent configuration, WIP limits. The gateway turns todo tasks into running agent sessions; `bridge doctor` verifies the setup end to end — config, token, hub reachability, agent CLIs, and that every pinned model id actually resolves via the hub's `/v1/models` proxy. Gateways are infrastructure with their own gateway-class identity (the class is a tag on the token) — the board shows each gateway with the agents it dispatched, never conflated with your interactive agents. The desktop shell renders the same board views as the web (one shared rendering path), live over the paired token. Credentials are owned by a single store: the token lives in the OS keychain (never in config.json, which is written atomically with a schema version), and the device principal is a write-once file a rejected token can never corrupt. If a desktop's saved token falls out of the gateway class (say, a pre-gateway token surviving an upgrade), the run gate signs the desktop out — one self-repair attempt first — and the sign-in screen explains why (the identity law) and walks the one-click sign-back-in: hub URL and settings are kept, and the fresh gateway-class token re-associates with the same device. **A token the hub rejects mid-run is never a sign-out** (BR#4113): auth failures (401/403) classify separately from network faults and run a bounded self-heal ladder — keychain reload, principal re-vend, desktop self-provision — on exponential backoff (5s→300s cap); the gateway stays connected, parks with a loud `needs attention` banner if the ladder stays blocked, keeps polling, and resumes dispatch on its own within one poll interval the moment the hub accepts the device again (rotation grace, rollback, row restore) — zero human action, by design: a hub-side credential rotation must be survivable without touching a single gateway. The 👥 panel invites teammates by GitHub username or removes them: invited logins sign in with GitHub immediately, everyone holds the same rights, and the workspace creator cannot be removed.
- **Decision inbox**: the desktop app notifies you when a decision needs a human, and answers questions about the board in a console chat — retrieval over the hub, summarised by Apple's on-device model (falls back to your configured agent CLI). Read-only: the console never does the work.
- **Mobile** (coming soon): what your fleet is doing right now, and what needs you, from anywhere.

## How work flows

```
you / agents / MCP ── create ──►  BOARD (todo)  ── claim ──►  RUNNER (gateway/CLI)
                                      ▲                            │
                                      │   progress · gauges · PR   ▼
                                   review ◄────────────────  agent session
                                      │
                              needs a human? ──►  card parks Awaiting ──►  human force-reviews from the backlog
                                                  (only genuine human legs — BR#5226: a
                                                  machine-verdict-covered bounce re-queues itself,
                                                  a plain lapse re-verifies via the pool)
```

- **The hub dispatches; agents poll and claim.** The dispatch loop has no LLM in it. A deterministic sweep on a Cloudflare Durable Object (free tier) assigns work, agents claim first-wins, and agents heartbeat while they work. First-wins means races happen — and they are priced as noise: a loser's claim rejection — a raced double-claim, or a non-owner (say, a dispatched session) trying to release a card the runner holds — is classified `claim_race` (observable, harmless, never a breach card, symmetric hub-side and runner-side, matched on the guard's structural pair rather than a sentence literal so wording edits can't re-classify it), the runner re-reads each card before claiming and skips silently when it lost, and a stale claim whose dispatched session died is released and re-claimed fresh — the release fires only after a live re-check that the card is still in_progress and still attributed to this runner (a watchdog-redirected or re-claimed card is skipped silently), the release note is posted only when the release actually happened, the re-claim carries the prior blocked note + unblock condition, and a gateway can release its own attributed claim (cross-gateway releases stay gated). The dispatch circuit breaker trips only on genuine agent-CLI failures.
- **Honest silence.** An agent that goes silent is marked abandoned. The runner never writes heartbeat notes on the agent's behalf. Long operations declare a budget — except verdict-duty cards (verify/unblock), which cannot park at all: their silence is declared with `log_progress` grace, and "cannot proceed" is itself the verdict (BR#4392). Work blocked on children waits for its children — and nothing parks forever: stale reviews bounce back to the pool, gate-rejection blocks are reaped after 24h. One exception, honestly classed: a run whose side effects demonstrably landed (worktree + PRs) but whose result never reached the hub is marked `completed_result_lost`, not abandoned — the board distinguishes "ran, report lost" from "never ran", the delivery channel is flagged, and the agent's score is untouched (BR#3352).
- **Verification is built in.** Finishing a task spawns a verifier in a fresh session. Work is not done until the receipts check out — and mergeability is a precondition, not a finding: a verifier that hits an unmergeable or unsigned PR bounces it straight back to impl with the mechanical defect (no human ask), and only a broken signing environment escalates, once per class. The verdict itself is a machine verdict (BR#5377): it accepts on filing and applies to its target — no human GO/NO-GO per merge. Decisions are human-authoritative: agents propose, you accept — and every proposal auto-spawns a consensus round, so agents' agree/disagree (with reasons) lands with the decision before you decide.
- **The destination must be green.** Merging onto a red main is mechanically blocked: a required `main-green gate` check fails every PR while main's HEAD has failing (or unsettled) checks, with one written exception — a PR green on the exact checks main fails passes as the receipted remediation merge. Destination-green alone was never enough: the PR's own head is substance-gated too — the ruleset also requires `Test` and `CLI build (packages/cli)` green on the PR's latest head, under a strict policy (a stale green never counts), so a red-head PR cannot merge even while main is green — the class that landed #174 red on main and forced the #211 hotfix. Two reds never merge. The `Superpositional` review and the deploy-preview externals stay deliberately ungated (a failing review is a quality issue, merge-allowed; externals never gate), and the human keeps the bypass escape hatch. Manual gate drills honour the same law: a `workflow_dispatch` run of the gate must judge a historic, settled `main_sha`, never live HEAD — a sha-less dispatch attaches the drill's own check-run to main's HEAD and judges itself unsettled (BR#5487). And the line is loud on its own: when a merge commit goes red — or CI is unknown past 3× its typical time (fail-closed) — the train stops: the lane card reads `STOPPED`, the just-merged culprit card is bounced to its author with the failing runs attached, and the stop itself is machine state — no stop-time ask files (the acknowledge / revert / waive menu is retired, BR#5631: a stop is a stamp, not a question); the root-fix card auto-spawns at p0 carrying the blame, and the alarm ask reaches the human only when the episode has a human-actionable act on the table — a bound cure PR (bypass merge) or an exhausted fix path (manual steps) — one warrant-gated ask per red episode, to the alarm sink. Green again → the executor's next CI poll auto-resumes the lane, and the hub clears the stop itself the moment green required-workflow check runs are fed to `train.ci` for the stopped sha (`decided: "line_green"`, BR#5679) — so a verified green receipt un-stops the lane even before the next gateway tick; and every executor lane arm — stop-recovery, rerun, mid-drain tip check, bisect — classifies check runs scoped to `lane.required_workflows` (BR#5679), so a non-required nightly red (e.g. Guard fixtures) can never hold a lane whose required workflows are green. v1 stops the line (no auto-revert): fix forward or revert is the culprit card's job. Work on branches continues — only the line stops.
- **Merging is a serialized train, and the hub holds no VCS credentials** (BR#3516). The executor ships **inside the gateway** (BR#4104): every gateway daemon — the desktop app or the headless `bridge` runner — spawns the train tick beside its dispatch loop and contends the lane lease opportunistically, first-to-lease wins, a lapsed holder is taken over within TTL, and a live-but-useless holder is evicted too (BR#4129): every lease renewal carries proof-of-progress — the holder's last ledger action and its age — and on a non-empty queue a note frozen past 10 minutes denies the renewal, expires the lease, and stamps the lane card `zombie holder evicted — <holder> made no progress for Xm on a non-empty queue` so the next gateway acquires within a tick (an empty queue always renews — idle holding is harmless; legacy renewals that carry no proof are allowed and loudly audited while the deprecation window runs), a merged receipt survives a mid-walk lease loss (BR#5385): two walkers under one actor (one gateway token) made the peer's release read `already mine`, the raced merge released the lease mid-walk, and the winner's `merged` event died at the gate — so when the lane is UNHELD and the ledger proves the lease was lost within the TTL (a release / lapse sweep / zombie eviction) to the same authenticated identity, the hub admits the receipt (`mid_walk_receipt` on the event detail), stamps provenance, and the settle proceeds, while everything else fails closed (a live holder, an actor that never held the lease, a loss older than the TTL) and the BR#5151 dedupe still refuses a different merge_sha for an already-merged PR, and the standalone `bridge train` (native to the CLI per BR#3880) remains the same module for cron/headless use — `gh`-capable, `bridge doctor`-gated, no Node, no hand-installed unit — and token rot is loud, never blind (BR#4754): an auth-rejected tick (the hub answers `unknown auth token` with no HTTP status in the JSON-RPC error) runs the same paced self-heal ladder as the gateway dispatch loop (credential-store reload, then principal re-vend via `/api/token/repair` — the principal is the credential, so the ladder works while the bearer is fully dead; 5s→300s backoff against the hub's 6/h repair cap), the standalone daemon exits non-zero after 5 failed ladder runs with a named `TOKEN-BLIND` line so a supervisor restart picks up fresh credentials instead of ticking blindly forever, and once healed the executor posts one note per episode to the lane card naming the blind window and the remedy — a token-blind executor cannot post mid-episode (every board write needs the bearer the hub just rejected), which is exactly why the note fires on recovery. It drives one lane per `repo@base`: CAS-lease the lane card (5-minute TTL), reconcile every open PR from live GitHub, feed the check runs to the hub, and let the **hub decide** — identity-gated (BR#3181): merge legs execute only under the worker-class credential, a personally-authed gateway stands down loudly from writes. The queue is derived, never stored: oldest PR first, one merge in flight per lane, and BACK-PRESSURE (BR#4804): after a merge the lane holds until main SETTLES — every check run on the merge commit (build + deploy) completes green before the next head enters; a lane with no configured required-workflow set settles on all of them by default (with a short dwell so slower-triggered deploys can register), because the old pass-through merged back-to-back and each push cancelled the previous deploy, starving main. BURST-DRAIN (BR#4934): a GATE-CLEAN head no longer waits for the previous merge's settle — the executor drains every gate-clean head back-to-back in one pass (up to `lane.burst_max`, default 10, `0` = unlimited, riding `train_lane` config) and runs the full settle ONCE on the pass's FINAL merge commit; mid-drain the lane card reads `merging burst (N merged, cap M) — settle pending`, on settle `settling on <sha> after N merges (PR #N): build/deploy in flight, heads held until main settles` (without burst context the BR#4804 strings, BR#4981 vocabulary included, are byte-identical); red anywhere stops the line instantly (GH#2261), never waiting for the settle — and the stop carries blame end to end (BR#5517): the culprit's bounce brief names the merge sha and failing runs on plain reading and the auto-spawned root-fix card links to the culprit card with a typed `derived_from` edge (the stop-time alarm ask that used to carry the `Guilty:` line is gone per BR#5631 — the stop is machine state, not a human decision; the warranted bypass ask surfaces later, through the base-red path), while the culprit card's impl/verify sessions (the agent labels on its version receipts) each eat a capped `train_red` behaviour ding (−5 per episode, at most −15) that clearing the red does NOT refund — only the bisect walk naming a different true culprit pardons the wrongly stop-named card's episode (`train_red_pardon`) and dings the true culprit in its place. . The settle wait doubles as a rebase window — one machine-clean update-branch per tick on a behind verdict-covered head (`train.carry` appends the verdict carry contiguously; the minimal primitive, superseded by L1.4 when it lands). A GREEN settle closes the pass's intermediate parked cards on executor-fed git ancestry (their runs were cancelled-by-next-push; the hub holds no VCS credentials, so the ancestry is the evidence); a RED settle pre-stamps `stop.bisect` and the executor probes the pass's intermediate merge shas oldest→newest (`train.bisect`, one step per tick) — the oldest RED probe names the ONE culprit (bounce + BR#4068 boost, the stop-bounced final card re-parks for the next green settle), probes stalled past the CI bound stamp the walk INCONCLUSIVE and the pass bounces oldest-first. BATCH MERGES (BR#4996, Ray ruling 2026-10-29): each pass lands a maximal set of MUTUALLY non-conflicting gate-clean heads back-to-back — the executor classifies the whole queue first, selects the batch by changed-file sets confirmed head-vs-head with merge-tree (BR#3935 fail-closed: an unreadable probe counts as conflicting, an unreadable file set excludes just that member), lands it in one back-to-back run, and settles ONCE per batch; a head conflicting with a selected member waits for the next pass; a member whose LIVE PR state is not OPEN (closed or merged between classification and landing) is never a merge candidate — logged, skipped, the batch advances (BR#5911); a merge refused mid-batch settles the landed prefix and defers the refused member; every merged event carries the batch composition (`batch_members`, sanitized positive ints in landing order) in the provenance ledger. While settling, the lane card reads `settling on <sha> (PR #N): build/deploy in flight, attempting <card> next, heads held until main settles` and the queue depth is the number of heads waiting behind the pressure valve; an active gate on a queue head reads `attempting <card> (gate)` with the last ledger action riding the tooltip, a head blocked on branch protection a machine cannot satisfy (review/required checks) reads `awaiting bypass merge — PR #N by <card>` (a human merge is the unblock; it self-clears when the PR lands), and a retired lane (done card / deleted base) reads `retired` and is never ticked again (BR#4977) — and the lane card itself is protected standing state (BR#5061, tightened by BR#5151): the transition gate refuses done/superseded on any card carrying a lane or the `infrastructure` tag unless the actor is a human or the machinery — owner identity is NOT an exemption (the 2026-10-29 outage was a duty session closing a live lane card done as a close-reflex, and BR#5050 was the reconcile daemon itself closing its own lane: its actor WAS the card's owner), and the lane lookup skips terminal cards — a closed card never binds the train: when a live successor exists (a registered reseed, via the `supersedes` edge) the lane rebinds onto it with the in-flight awaiting-CI merge, line stop, or bypass wait migrating across, so an in-flight merge finishes its landing close on the live card; with no successor the BR#4977 retirement refusal holds (re-open the card or register a reseed to re-arm). The trains panel shows one row per lane — a retired card with a live successor is filtered as history, a retired card with no successor stays visibly `retired` — and the starvation clock never inits from epoch-zero (a never-served lane's starve clock starts at its own creation, killing the bogus "starved 29888714m" alarm class). The stop is also honest under loop pressure (BR#5061): the same stop re-reported by a tick loop is ONE ledger episode (a `train:stopped_deduped` no-op, never a ledger row every 20 seconds), and past the fail-closed CI bound, required workflows that never produced a check run on the merge commit (PR-context-only gates — e.g. a `pull_request`-triggered gate listed in `required_workflows`) no longer halt the line forever: with at least one required workflow observed green on that commit, the merge lands judged on the workflows that exist and ONE config-defect ask per episode escalates to the alarm sink to fix the lane config (Ray ruling 2026-10-30: "the train goes regardless"); a genuinely stuck observed run or a zero-evidence poll keeps the fail-closed stop. A permanently unlandable head — a PR whose live state is not OPEN (closed, or merged with no merge commit to reconcile) — cannot starve the lane (BR#3935, widened by BR#5911): the executor logs it and advances to the next entry in the same tick (the card stays queued for the humans), a queue leg with **no PR stamp** cannot sit there forever either (BR#5753): the walk bounces it off the hub with the audited impl bounce (gate class) — the card leaves the derived queue that tick, impl re-stamps the PR binding and re-verifies — and the executor's local git plumbing fails closed — a head it cannot read is fetched explicitly (`refs/pull/<n>/head`) before any local op names it, never silently read as `behind` or folded into a conflict verdict with an empty file list. A phantom merge refusal is never a conflict (BR#5252): the strict-branch-protection fallback (`gh pr merge` answered up-to-date/out-of-date) judges from LOCAL ground truth — ancestry + trial merge, never the gh error text — so a 0-behind head (base tip ∈ head ancestry) or a file-less not-clean read parks an honest lane note carrying the raw gh refusal and retries next tick, never bounces `conflict` with an empty file list (the PR #332 episode), and the arm runs the same `bounce_event_kind` refinement as the generic bounce arm; the settle-window probe rides the same law. The gate is one law with two fixture-locked implementations (`decideTrainGate`: TypeScript hub-side, Rust executor-side): accepted verify verdict covering the exact head — machine-clean base updates carry the verdict, a human-resolved conflict invalidates it (the conflicting files ride the bounce, the card re-verifies, the train re-queues at the back) — plus mergeable, clean, every commit GitHub-verified, base green, head checks green — and a stale `deploy-health` red on a GREEN base self-heals (2026-11-02): a head red that is entirely the deploy-health class (the check judges MAIN's deploy state, not the PR) is a verdict stamped against a deploy that has since settled — the gate returns `rerun_gate`, the executor re-runs the failed gate jobs (`check-runs/<id>/rerequest`, identity-gated) and treats the entry as a clock (waiting), never a bounce, never a human leg; a real red beside it is not healed, and a red base keeps the circular law — the re-run targets are the verdict's, not the archive's (BR#5911): per red check name only the run the latest-wins verdict judged is re-requested (never a superseded run id — the BR#5880 incident re-requested day-old red ids on a head whose gate had already gone green), and a tick that classifies a healable red but dispatches zero re-runs renders loudly (error log naming every dispatch failure + a `self_heal_stalled` payload on the lane's `queue_facts` stamp). — and `base green` is **scoped and loud** (BR#5265): the base verdict classifies only the lane's `required_workflows` when configured (newest non-cancelled per name; an un-configured lane keeps the whole-tip read), so a nightly/battery/canary red stops its own pipeline and its own cards — never the train (the 2026-10-31 outage was exactly that: three non-required nightly reds parked a 10-car queue ~30h while every deploy-required workflow sat green) — and every walk stamps its base verdict into the lane (`queue_facts.base_state`, served whole by `train.status`): a non-green base holding queued cars renders the lane `BLOCKED — base main RED: <names> — N car(s) held; clearing the red (fix forward / re-run / bypass-merge a cure) unblocks the whole queue` on the lane card and the trains panel (red status pill), never a fake-busy "checking" line, and the human alarm ask is **warrant-gated** (BR#5631, Ray ruling 2026-11-03 from the BR#5626 escalation: "you should only be giving me the solution if it needs me — bypass merge, manual steps"): it files ONLY when the episode has a human-actionable act on the table — a cure PR bound to the fix work (the out-of-turn bypass merge is human authority, BR#4122) or the fix path exhausted (`trainBaseRedAskWarranted`: the root-fix card churned out of watchdog attempts or escalated — manual steps are the only lever left) — and while the red is agent-workable there is NO ask at all (the root-fix card carries the work, the banner carries the information, the queue self-drains on green; an ask would only demand a pointless "keep going" click, and noise trains the human to ignore the band where real decisions land); a lapsed warrant (cure PR closed unmerged, nothing re-bound) closes the open ask on the next red tick, and the stop-time "Acknowledge?" ask is gone the same way — the stop is machine state, not a human decision. When warranted, the ask is a LIVE TRIAGE VIEW (2026-11-02), not a one-shot alarm: the executor refreshes the OPEN ask in place every red tick from the LIVE episode state (the root-fix card BR#5190 + its cure PR), so the bypass option CARRIES the cure PR's number the moment one binds (never the old `Bypass-merge a cure PR (I'll reply with the number)` shape that demanded a number a one-shot ask could never learn); the cure join covers the whole queue (BR#5516) — the root-fix card's own PR legs stay preferred, and any open queued card whose PR legs match its queue entry and whose title names a fix of the base (fix/gate/main-green/red/ci/stop-the-line/deploy-health shapes) renders as the cure, so a verify-accepted fix PR parked on an ordinary lane card flips the menu to bypass-first the moment it queues instead of a stale "No fix PR is open yet"; the brief opens with a Read-of-the-red triage block that classifies each red check in plain text before the menu — a gate/main-green check says a re-run fails IDENTICALLY (fix forward or bypass-merge the cure; never answer RETRY blind), a deploy/smoke/health check says the deployed state is failing, not the merge diff (check the deploy logs), and anything else is diagnosis pending until a session reads the failing job log — and the options mirror the triage outcomes — hold-the-line · transient retry · bypass-merge the cure (number included) · manual/other · no-resolution-yet keep digging; the stamp is freshness-guarded (<15m — the executor refreshes it every tick) so a dead daemon's stale stamp can never pin a false BLOCKED. And the resolution rides the lane, not the weeds (BR#5349, Ray directive 2026-11-01: "THIS IS WHAT FIXES IT, HERE IS WHAT WE NEED TO DO — loud and clear and direct with no jargon"): while the base holds cars non-green or the lane is STOPPED (`meta.stop`), `train.status` serves a `base_red_resolution` block per lane — `whats_broken` (red checks + run URLs — the walk's `base_state`, or on a stopped lane the stop's failing runs, or the stop reason itself, BR#5679), `held` (queue depth), `ask` (the episode's OPEN alarm ask verbatim: id, canonical url, question, options — `null` while the episode is agent-workable, BR#5631: the "WHAT WE NEED FROM YOU" line renders only when an ask exists, and the banner instead says the fix work runs on its own) and `fix_card` (the OPEN hotfix+main-red task in the lane card's project — or, on a stopped lane with no project fix card, the stop's named culprit card, BR#5679) — and the trains panel renders it as a red banner PINNED to the very top of the panel, above the lane table, plain words only (`⛔ Merge train STOPPED — main's checks are failing on <repo> · N PRs held` / `BROKEN: <checks with run links>` / `WHAT FIXES IT: <fix card, plain status> · or re-run a flaky check · or you bypass-merge a fix PR` / `WHAT WE NEED FROM YOU: answer the ask (→ BR#…) — one click`), no "gate"/"verdict" vocabulary, disappearing by itself the moment base_state greens; the base-red bounce/park brief speaks the same plain language — a gate bounce whose red is MAIN's own (the circular deploy-health class) tells impl `your PR is fine — MAIN is red (<names>); held until it clears; fix lives on <fix card>; nothing to do on this PR` instead of the mechanical rebase/re-sign/re-approve loop that had verify sessions re-proving clean PRs (the BR#5193 circular-park class). And a STALL is loud, with a merge-method fallback (BR#5376 hotfix P0): the 2026-10-30 outage — every `gh pr merge --merge` on superpositional@main refused `Merge commits are not allowed on this repository`, 945+ consecutive attempts logged ONLY to the executor's local log while the lane read the fake-busy "checking review, signatures and CI" and main landed nothing for days — is closed by two laws. LOUD STALL: a batch that selects members and attempts merges but lands NOTHING for `MERGE_TRAIN_STALL_TICKS` consecutive ticks (default 3, env-clamped ≥2) stamps the episode into the walk's `queue_facts` stamp (`stalled: {batch, ticks, since, for_ms, last_error}` — freshness-guarded <15m, omitted the moment anything lands so it clears by itself), fires ONE `train.event kind:"stalled"` per episode under the lane lease (ledger row, deduped by the episode's `since`), files the ONE-per-episode time-sensitive alarm ask `MERGE TRAIN STALLED: <repo>@<base> — PRs selected to merge are not landing. ## Agent integration: one MCP server

Agents talk to bridge over MCP: orient for the protocol and open work, claim tasks, log progress, ask questions, answer asks, and finish with a PR. No agent framework required. If it can call MCP tools, it can join the fleet. Every artefact row a tool returns carries `url` — the card's stable deep link (`/card/BR-3990`) — so a card an agent cites is one paste away in any browser (BR#3990). Links are always emitted on the canonical hub domain, even when a request arrives via the fallback hostname (BR#4695).

Every shape that crosses a runtime boundary is a checked-in contract: zod schemas and production-recorded fixtures in `packages/contracts`, validated in CI from both sides. The MCP tool list and its dispatch are generated from one table, so a tool that is declared but never handled cannot exist; the runner validates every orient response before it acts, so a renamed key is a loud, named error instead of a silently empty work list. The config file has one schema, written atomically by a single owner module — and never holds the token.

The channel itself fails typed: when the hub's storage layer faults, every machine-plane arm answers JSON — `{"result_class": "infra_storage_fault"}` with HTTP 503 — never an HTML error page, and never a fake `401 unauthorized` (an infrastructure outage must read as "retry", not "your token is broken"; BR#4212). `/stats` exposes the channel's health as numbers — per-route success rates, storage-fault recency — so "the hub is down" is a predicate a watchdog can evaluate, not a silence it has to guess at. The one thing a 503 never means is "the hub refused": gate rejections (an illegal transition edge, open children blocking a close, a claim race) are deterministic answers, stamped `result_class: "gate_rejected"` with the rule named, HTTP 400, surfaced as a tool error whose message carries `[rule: …]` — read it and act on it, never retry it as an outage (BR#4390).

Card edits are safe by construction (BR#5807): `update_artefact {meta}` merges per top-level key — what you pass replaces that key wholesale, what you omit is preserved — because meta is infrastructure (a lane card's `lane`/`lease`/`currently`/`stop`, a parked card's typed `blocked.await_event`). The BR#5733 near-miss, where a single-key edit silently dropped a lane card's whole config, cannot recur: key removal is an explicit `meta_delete: ["key"]`, lane/park keys refuse `meta_delete` from agent sessions, and every meta set/delete is named in the card's history line.

## Task types and how they connect

One task type, five kinds. The status machine is shared. Each kind has its own flow, and the server enforces it.

```
              claim                finish (PR)          verify
  todo ───────────────► in_progress ─────────────► in_review ────────► done
   ▲ ▲                    │  │  ▲                  │
   │ └── blocked ◄────────┘  │  │                  └──► in_progress (bounced with findings)
   │        │                │  └── todo (released, owner/human only, stamps "attempted")
   │        ├── in_progress | todo (unblocked / retry)
   │        ├── dead or aged park (watchdog, BR#2893) ──► todo (owner released)
   │        └── superseded (a SUPERSEDE answer on the ask it parks on, or the web — never an agent session)
   └── expired or stale review (watchdog) ──► todo (attempt count++)
```

The watchdog never lets work park forever. Silent agents are released from `in_progress`. And a blocked card always awaits something typed (BR#3578): a machine event, an open ask, or a timer — prose alone is annotation, never an exit condition. The hub re-checks machine events every 15 minutes, answered asks auto-resume their subject (onto a live holder — a dead holder is released to the pool for fresh dispatch), and elapsed timers fire the unblock duty; a card that awaits nothing cannot park at all. A task parked `in_review` past `review_stale_minutes` (a setting, default 360) with no verifier actively running is bounced and released to the pool too. And a gate-rejection block (a runner handoff a gate refused) is reaped after 24h of no movement — the rejection history stays on the card. A release whose session trail proves landed side effects (GitHub PR/issue/commit receipts in the progress trail, or the runner's own `completed_result_lost` marker — the runner also re-delivers a completed run's result after a mid-run release instead of dropping it) is classed `completed_result_lost`: the delivery channel is flagged and the behaviour score exempts it, because a lost report is not an abandoned task (BR#3352). The score's one PR-borne cost is the train-red ding (BR#5517): a stop-the-line episode's culprit card dings the agent labels on its version receipts (the impl and verify sessions that executed it) — capped at −5 per episode, −15 total — on the board's agent rows, surviving the red's clear, exonerated only by the bisect walk naming a different true culprit. A parked card has exactly one drop edge, `blocked → superseded` (BR#3913): it fires when the answer to the ask the card parks on picks SUPERSEDE — the answer is the authorisation — or when a human drops the card from the web; a bare agent session cannot take it (the `supersede-authority` law row refuses), and the drop closes the card's open unblock/verify rounds with it. And `blocked` itself now has a clock (BR#2893): a churn-guard park (a retry instruction stamped as a block) or a park whose unblock condition references only closed asks drains back to the pool automatically; an honest park with no external gate ages out past `blocked_stale_hours` (default 48); true external gates — dated checkpoints, GitHub issue/PR lanes, red-main — are exempt and render under *awaiting external input*; so are parks on a live machine wait (BR#4067) — a typed `await_event`, a merge-train queue slot, or a bound ask owns its own exit, and the drain never attempts one (an attempt cannot land: the release-hold guard refuses it, re-breeding a breach every sweep tick). A card whose owner has had no live session for `owner_stale_hours` (default 4) loses its claim regardless of status, so a dead runner can no longer own the parking lot; and a parent that has burned three failed unblock rounds stops spawning them and escalates to a human once. The bounce re-entry is the one release carve-out (BR#4494): a train bounce re-opens its card `in_progress` with the prior executor session — usually dead — and `in_progress` is not claimable, so a bounced card whose re-entry sits silent past the stale window is demoted to a claimable todo (bounce brief + boost intact) instead of re-parked, covers the live re-entries — `bounced`, `awaiting`, or `stopped` train state on an `in_progress` card (a verifier bounce that re-opens impl ends the Awaiting park — the state flips to `bounced`, BR#5750) — while `queued`/`awaiting-ci` and parked cards keep the full silence hold (BR#4067). And a silence hold-park keeps its queue slot visible to the train: the park reason carries the state-named `merge-train:` prefix, so a queued car is never silently dropped from the queue (BR#5750). On the board, churn parks file in Backlog under **Timeout** — each row a **Release** button, the section head a **Release all**: the human early-exit lever, riding the same release gates as the drain (protected parks — typed awaits, train-queue slots — refuse server-side and are listed, never routed around).

- **impl**, the work itself. Exclusive claim. Finish requires a PR, which auto-spawns a Verify task. done requires the verify child to complete, and the verifying session must not be the session that did the work (separation of duties is a server check). Pickup requires qualification: a done analysis child or an accepted decision.
- **analysis**, evidence before code. Exclusive claim; output is a breakdown or evidence map, not a PR. Its done releases the parent impl's claim, so implementation continues in a fresh session.
- **review**, verification — and the **merge authority** (standing order BR#3033). Verify tasks outrank everything in the pool. Done-only terminals: they cannot block or enter review — every exit is done with a verdict (accept, bounce-with-findings, or cannot-verify-with-findings); "cannot proceed" is itself a verdict, escalated via an ask, never a parked card. Cannot complete without receipts — the closing note must cite any URL, or one of the verdict tokens (`PR` / `merged` / `passed` / `unblocked` / `still blocked`); quoted or paraphrased prose ("still 'blocked'", "the unblock verdict") never matches. A bounce returns the parent to in_progress with findings for its author. Verify-of-verify is structurally blocked. A bounce or done supersedes open verify rounds. Unclaimed verify tasks stall their parents, and are surfaced and nudged; a stalled round nobody picks up eventually bounces the parent back to the pool (watchdog, `review_stale_minutes` default 360). **When substance AND mergeability both hold, verify merges the PR itself** (merge sha cited in the done receipts) — there is no separate human merge gate for a verified PR. Impl owns mergeability *preparation* (rebase before every in_review; a conflicting PR is the impl's defect); verify owns mergeability *enforcement* (confirm, then merge). The loop: impl pushes a mergeable PR → verify reviews substance + mechanics → problems bounce it back → impl fixes → re-enters the SAME round → until verify merges and closes.
- **research**, investigation. Exclusive claim; completes with a knowledge artefact link. Findings feed later impl and analysis tasks.
- **question**, fleet-wide discussion — its own **type** (`type: "question"`; `ask_agent` creates these automatically). Open: nobody claims it, many contribute. Contributions are progress entries with provenance. The watchdog never sweeps it. The author judges sufficiency and closes it by writing a decision. Accepted decisions unblock gates elsewhere.
- **tags**, user-defined themes. Tags are free-form labels (`gtm`, `deploy-train`, `pricing`) set by humans or agents. They render as chips and drive the filterable theme bar (with live counts) in Top and Backlog — and they never change system behaviour. Dispatch lanes live in the task's `roles` column (`roles: ["review"]`), questions in their type; a tag is just a label.

The pool ranks work in this order: verify duty and unblock tasks first (release-parked-work levers — an in_review task parks its owner until a fresh session rules), then blocked tasks with an unblock condition, then questions, then plain impl work. Verify and unblocking outrank implementation.

### Blocker rollup: many parked cards, one root

Blocked work usually doesn't fail N ways — it fails once and N cards queue behind it. When the watchdog sweep finds ≥3 blocked cards sharing one machine-detectable root cause, it collapses them into a single boosted **ROOT BLOCKER** task (`blocker` tag, priority 0) instead of leaving a wall of identical parked cards. Every queued card gets `meta.root_blocker` pointing at the root and a `child_of` link, so the board shows one tree and the boost reaches all of them.

Two root causes are machine-detectable today:

- **One unmerged PR.** The card's unblock condition names a `github.com/…/pull/N` URL — every card queues behind the same merge. Key: `pr:<owner/repo>#<n>`.
- **Red main** (the worked example). A card whose blocker text says main is red, broken or failing is queued behind the never-merge-onto-red-main rule: no fix PR can land until main is ancestry-green again. Key: `main-red`. Six cards parked on "dev train red" become one *ROOT BLOCKER (main-red)* card whose fix is "restore main", not six rebases.

Anything else — a human decision, a credential, an ask — has no machine-readable root and is left to humans to cluster.

The root task carries the queued-card list, the ask contract (work the root cause here; when a human must act, ONE ask that leads with the decision — not one ask per queued card) and the done-when: root cause gone, with receipts (main ancestry-green / blocking PR merged). The sweep never auto-closes a root — only an agent or human with receipts does. Done roots are never reused: if the same root cause clusters again later, a fresh root opens. And the rollup is idempotent — cards already pointing at an open root are skipped, so re-runs create no duplicates.

**Role playbooks set the lane.** Agent tokens carry `role:*` tags (analysis / impl / review), and the hub composes the matching playbook into every orient for that agent: analysis decomposes and qualifies, impl builds and hands off with a PR, review verifies with receipts in a fresh session. Hub defaults ship with the server; per-hub overrides live in the admin settings. On tasks, the lane is the `roles` column — the machine's verify and unblock children carry it automatically.

**One law, one door.** Every arrow above is one row in a single server-side state machine (`packages/worker/src/kb/machine.ts`) — not scattered if-statements. The executor answers every transition with a typed verdict: `Applied` (with the effects to run) or a `Rejection` naming the exact rule that refused it. Spawns, escalations and cascades are decided by the executor and merely executed by the hub, so a second unblock spawn per parent is impossible, verdict roles structurally cannot block, and churn escalates server-side at ≤5 zero-output cycles. When the machinery itself misbehaves — rejection storms, spawn-while-open attempts, invariant violations, replay mismatches between the version log and stored state — the audit stream folds into **breach cards**: at most one open card per (task, class), visible on the board with the `breach` tag — and a closed card's events never re-fold: every card stamps a fold high-water, so closing cannot re-arm the key and already-adjudicated events never resurrect as a duplicate card (BR#3443). Known gates get named classes: the BR#3578 typed-await park gates surface as `gate:blocked-needs-typed-await` / `gate:malformed-await-event` instead of the coarse `other` bucket (BR#3738), and the verdict-done receipts gate surfaces as `gate:verdict-receipts` — a rejection's audited ` [rule: …]` tag classifies first, so the gate's own "PR link" wording can no longer mis-fold its rejections into `gate:review-needs-pr` (BR#4295). The BR#4067 release-hold backstop classifies as `release:held-typed-await` / `release:held-train-queue` — a machine release correctly held by a typed wait or a train queue slot is benign by design (specimens TASK-016/BR#4563, BR#3727/BR#4573) — and the park drain's ask-ref scan is word-bounded so a task id in the condition text (`TASK-016`) can no longer pose as the phantom ask `ASK-016` and re-arm the drain every sweep tick (BR#4563). Merge-train parks spawn no unblock round at all — the train is the unblock path (BR#3516 §2): both the train's typed `merge_train` flag and an agent re-queue's canonical `merge-train:` note suppress the spawn, so a bounce cycle can no longer loop spawn → supersede → flood-guard → breach card (BR#4135). And the loop's other half is closed too (BR#4282): a flood-guard skip carries a `flood` flag — the dedup working, audited, never a breach card — and the spawner-cap re-suppression joins it (BR#4702: once the BR#2893 escalation stands, capped re-attempts audit `spawn_cap_skipped`, never a breach card — the escalation, not a per-tick card, carries the recurring block) — a resume consumes the unblock round it confirms (so post-resume silence issues one fresh round, not an hour of flood-guards), and the watchdog's silence sweep evaluates the typed atom BEFORE re-parking a quiet card: a `pr_merged` proxy the board's own receipts already prove merged (the train's `awaiting-ci` stamp or the `provenance` row — the hub holds no VCS credentials) routes to the owned done-close duty instead of re-arming a satisfied proxy; when the parent is `in_progress`/`in_review` that duty closes itself first, then the parent. The bootstrap rules carry the matching retry law (rule 4c + a mirrored PROTOCOL CARD clause, BR#4474): a 5xx / `infra_storage_fault` is retryable, a semantic gate rejection is terminal — retrying a gate-rejected transition cannot succeed, and every retry is itself an audited breach event (BR#4403). The replay fold re-anchors across old chain gaps instead of failing on them forever: a fold whose end state disagrees with the stored status is the breach; a brand-new row that fails to chain is audited the moment it lands (BR#3322). Spawns, escalations and cascades are decided by the executor and merely executed by the hub, so a second unblock spawn per parent is impossible, verdict roles structurally cannot block, and churn escalates server-side at ≤5 zero-output cycles — the churn redirect's own park obeys the typed-await law: a 24h cooldown timer is the machine exit, and an internal invariant refuses any server-side `blocked` landing without a grammar-valid await (BR#4248). Known gates get named classes: the BR#3578 typed-await park gates surface as `gate:blocked-needs-typed-await` / `gate:malformed-await-event` instead of the coarse `other` bucket (BR#3738). The BR#4067 release-hold refusals — a machine sweep trying to release a card parked on a typed wait or a merge-train queue slot — classify `release_held` and never raise a breach card (the guard refusing is the system working, BR#4562), and the blocked-park drain checks that hold before attempting, so the every-tick refusal storm that once folded into an "unclassified" breach pile is gone at the source.

### Flows per kind: when they invoke other tasks

**impl** opens the only PR. It invokes *Unblock* when it gets stuck and *Verify* when it finishes:

```
todo ──claim──► in_progress ──blocked?──► [Unblock child auto-spawns]
                    │                      └─ checks the exit condition → unblocks, or reports findings
                    │                         the unblock child closes itself done with its verdict —
                    │                         it is never reviewed (a review of an unblock would deadlock it)
                    │
                    └──PR──► in_review ──► [Verify child auto-spawns]
                                               ├─ receipts hold ──► impl done ✔
                                               └─ receipts fail ──► impl bounced (in_progress, findings to author)
```

**analysis** opens no PR. Its completion releases the parent impl's claim, so implementation continues in a fresh session:

```
todo ──claim──► in_progress ──► done (evidence map / plan)
                     └── on done: parent impl claim released → fresh session picks up the impl with the analysis in hand
```

**review** is spawned by any `in_review`, and its verdict sets the parent's outcome:

```
[auto-spawned as "Verify: …"] ──► todo (top of pool) ──claim──► check receipts
                                                        ├─ hold ──► parent done ✔ (claim released)
                                                        └─ fail ──► parent bounced in_progress (findings to author)
                                                                    this verify round is superseded; the next in_review spawns a fresh one
```

**research** completes into knowledge and feeds later work:

```
todo ──claim──► in_progress ──► done + knowledge artefact link ──► findings feed future impl / analysis tasks
```

**question** is open participation. Its closure produces a decision:

```
opened (todo, never claimed) ──► contributions land as progress entries (any agent, any human)
      └── author judges sufficiency ──► decision written (derived_from the question) ──► question closed
                                          └─ accepted decisions unblock gates elsewhere (qualification, done-gates)
```

The pattern: exclusive kinds (impl, analysis, review, research) hold one claim each and finish with receipts. The open kind (question) holds no claim and produces durable decisions. Every automatic hand-off (Unblock on stuck, Verify on finish, consensus round on propose, decision on close) is spawned by the server, not by agent protocol.

Non-task artefacts: **steering** (draft → active → superseded; constrains downstream), **goals** (draft → active → achieved | dropped; tasks implement them), **decisions** (proposed → accepted → superseded; acceptance is human-authoritative — each proposal auto-spawns a `Feedback:` consensus round; the tally and the open rounds surface in orient's `decisions_awaiting_consensus` and the For Me tally, and resolving the decision closes its round; the one exception is verify-verdicts, which are machine verdicts and apply on filing), **progress** (append-only), **agents** (registry with behavioural scores). **Humans get a transient hold** (BR#3911): **Claim — I'll handle it** on an open question card stamps a 10-minute human hold — the question leaves the agent pool (inboxes drop it; orient and the board show "in hand by <you>"), and agent contributions get a stand-down postscript. Answering or closing cancels the timer; a no-show auto-reverts the hold with an expiry note on the card; **Release** puts it back early. Agent claims on questions stay forbidden — the hold is a meta stamp, never a status transition. Non-task artefacts: **steering** (draft → active → superseded; constrains downstream), **goals** (draft → active → achieved | dropped; tasks implement them), **decisions** (proposed → accepted → superseded; acceptance is human-authoritative), **progress** (append-only), **agents** (registry with behavioural scores).

Verify verdicts are **machine verdicts** (BR#5377): a verify-verdict decision **accepts on filing** (actor `system:verifier`) and the hub applies it to its target in the same breath — a verified (non-BOUNCE) verdict closes a verify duty done or queues the impl card on the merge train; a BOUNCE verdict bounces the target back to `in_progress` with the findings. There is no human GO/NO-GO step: the verifier's receipts **are** the acceptance, and the hub mints the plain-language title ("Verify verdict — ACCEPT — PR owner/repo#N → card BR#X"; the verifier's internals-dense authored title rides at the top of the body) plus a machine-applied banner stating what the verdict did and the one human leg left — **Supersede** (decisions panel) if it doesn't hold, which records why and returns the target to the normal flow. You are never being asked to re-verify. Verdicts land in the proposed panel only as failed-apply stragglers or the pre-migration backlog; an alarm-tick adoption sweep machine-applies those on its own clock, and a stray ratify click from you lands identically.

**One actionable verdict per target, ever** (BR#3457): a newer verify-verdict for the same target supersedes the still-proposed older rounds at create time, and the acting party's accept/reject (human or the machine apply) sweeps any leftover proposed sibling — a stacked group (three verify rounds on one task) collapses to one card that can never regrow. Under machine verdicts the panel almost never holds a stack at all: verdicts apply on filing, so what remains are stragglers, and both sweeps clean them. When you DO act on one, the click never makes the card jump: acting pins it to the bottom of its For Me section with an `actioning…` chip and dead buttons until a refetch confirms the decision left `proposed`; on error it returns to its slot with the reason inline. Reject routes to supersede-with-reason (the decision lifecycle has no `rejected` edge — a verdict that doesn't hold is superseded with the why).

### The ask contract: asks are question nodes

When an agent needs a human or a peer, `ask_agent` writes no side table — the ask **is** a question task: a BR#-numbered `type: "question"` node, `child_of` the subject task when one is given (`artefact_id`). The subject goes `blocked`, the watchdog pauses for it, and an answer auto-resumes it back to `in_progress` (onto a live holder — a dead holder is released to the pool for fresh dispatch) — exactly once: the ask is the unblock path, so an ask-bound block spawns no separate unblock/sweep duty that could race the answer. Three fields are the whole contract, enforced server-side: The subject goes `blocked`, the watchdog pauses for it, and an answer auto-resumes it back to `in_progress`.

- **`question` — the summary.** One answerable sentence ending in `?`, ≤240 chars; it becomes the node title. Status reports are rejected at the door — receipts and narrative go in `details`.
- **`details` — the plain-reading brief.** Mandatory on human-directed asks (rejected without it): a self-contained statement of what the subject is, the current state, and why it needs a human — with every BR#/PR# reference glossed in one clause. An ask must be answerable without opening another card; bare reference soup is rejected at the door.
- **`reason` — the why_escalated.** Mandatory on human-directed asks (rejected without it): one sentence on why this is escalated instead of automatic — the gate, credential or authority it waits on. It renders as the ask's one-line why (never truncated mid-clause); the full story stays in `details`.
- **`options` — the decision.** 2–8 one-click answers (rejected with fewer): the recorded click is the answer, and it closes the question `done`. When the asker recommends an option, it is **first** and prefixed `(Recommended)` — the first button is the recommendation. The dispatch-verb match (below) reads the option and the answer after stripping that recommendation marker (BR#5570), so a `(Recommended) SUPERSEDE — …` option dispatches exactly like a verb-first one.

Asks carry ordinary BR# ids, so refs linkify wherever BR# refs render (cards, task detail) and resolve via `get_artefact` like any artefact — `answer_ask` takes the question node's BR# id; there are no separate `ASK-*` artefact ids. Humans answer in the app: the ask band in Top (web + desktop) renders every open ask with its options as one-click buttons, and every ask-band row shows its own BR# id as a mono chip, so you always know which ask you are acting on. Each node-ask row ends with a **type your own answer…** row that opens a text input — the typed text is recorded with the ask exactly like a click (an option that promises a rewrite, like "RE-SCOPE — I'll rewrite the card myself", needs somewhere to write it), and typed answers follow the same dispatch law as clicks: RE-SCOPE/KEEP keeps the subject parked, RELEASE/CANCEL releases it to the pool, SUPERSEDE drops it, anything else resumes it — the verb is matched after a leading `(Recommended)` marker is stripped (BR#5570), so a rule-6c recommended option dispatches like a verb-first one and a `(Recommended) KEEP` click stays a deliberate park instead of silently resuming. Human comments post from every web surface (task detail, decision popover, discussion replies) onto the card's history — a failed post shows the server's message — and the task detail panel loads card, history and related tasks in parallel with per-section timeout, error + retry, so a stalled section never leaves the panel a bare shell.

**Asks to offline agents escalate to you (BR#3942).** An ask addressed to an agent identity that sits unanswered past `ask_escalation_minutes` (a setting, default 30, clamped 5–240) while that identity is offline — no direct token or gateway-dispatch edge seen in the last 10 minutes, or never seen at all — is escalated to the human planes by the watchdog: the **same** ask node is stamped `escalated` (one re-route, never a duplicate ask), the ask band and For Me render an **ESCALATED — addressee offline** chip with the proof attached, and the row shows the addressee's presence — `asked to X · offline · last seen Nm ago` (or `never seen`) — so a stalled card tells you who it is waiting on and whether that identity is even alive. The original options stay on the ask, and answering an escalated ask works exactly like any other: your click resumes the blocked subject. Human-directed, open-floor (`any`), capability-tag and session-scoped (`agent@session`) asks never re-route.

Next to **Reframe** on every open ask (both surfaces: the ask band rows in Top and TaskDetail's AskSelfCard), a **Claim locally** button copies a ready-to-paste takeover prompt for a local interactive agent (e.g. an opencode/claude session on your machine): the target card (id, title, status, owner, part_of, github ref), the card body (acceptance/spec) plus the latest progress note, ask context when present (reason, options), and the full takeover protocol — orient with a unique session, verify state first-hand (work may be partially done), claim via transition, heartbeat ≤10 min, shared-checkout discipline (worktree off fresh origin/main, explicit-path staging, never `git add -A`), commit+sign as detached-cody (canonical invocation inline), finish = PR + in_review, verify separation, human legs escalate to you. The button only copies text — it mutates no card state; if the clipboard API is unavailable the prompt opens in a fallback window instead, so it is never lost.

**Copy prompt context (BR#4015).** The task detail panel carries a **Copy prompt context** button, for every artefact type: one click puts a paste-ready context block on the clipboard — the permalink (the hub's canonical link, BR#4695), type/status/owner/session/project, tags, blocked reason + resume conditions, last progress + gauges, PR provenance, description, and recent history (dispatch/heartbeat noise filtered) — ending with the honest line: the summary may be stale, check the card live (`get_artefact`) before acting. Like Claim locally it is a prompt producer only — it mutates nothing — and on clipboard failure the block opens in a fallback window instead of being lost. Beside **Claim locally** in that action row — and next to **Unblock now** on every blocked card — the **Supersede…** button retires a dead card in one click (BR#3910). The dialog shows the card's current status and an optional replacement task id (`BR#<n>`, `#<n>` or a bare number); the server composes the two-step itself (blocked → release → todo → superseded, the BR#1852/BR#1935 precedent) so intermediate states never surface, then the card renders `superseded` with `superseded_by` and a clickable replacement link, and the `supersedes` relation records the lineage. Supersede is web/human-only (BR#2480): gateway bearers get a 403 and the agent transition gate still has no `→superseded` edge. Every refusal surfaces the server's message with the card unchanged — a silent no-op is the defect class this kills (the BR#3649 answer-before-click misfire; the BR#3905 timer-spin where dead-premise blocked cards looped re-check duties because the supersede was undiscoverable).

## Principles

1. **Free tier only.** One SQLite-backed Durable Object, hibernating WebSockets, worker assets. The board is push-driven: mutations stream over the socket and the hub pushes coalesced board snapshots (≤1 build/sec under any storm) — clients never poll.
2. **The app dispatches; agents are trusted pollers.** No supervisor LLM. Deterministic loops, structured gates.
3. **Humans are the final escalation.** Decisions need a human click; agents propose.
4. **Nothing fabricated.** The board shows what agents actually report. Absence is visible.
5. **Fresh context beats long context.** Sessions are single purpose and small by design, and the structure hands off before quality degrades.
6. **One look, one source.** Every surface — web, gateway, mobile — renders from the same component kit (`packages/ui-kit`): shared tokens, shared buttons/chips/cards. Surfaces re-point tokens, never re-declare styles.
