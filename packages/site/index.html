bridge

Put your agent fleet to work. Watch every move. Sign off when it matters.

bridge is a control plane for coding-agent fleets. Tasks go on a board; runners on your machines claim them and drive real agent CLIs; every run reports live progress with confidence, risk, and completion; anything that needs a human lands in your inbox for one-click sign-off.

It is not a kanban tool and not an agent framework. It's the layer between them: the board where work becomes visible and dispatchable, whatever executes it.

Install

curl -fsSL https://raw.githubusercontent.com/state-vector/bridge/main/install.sh | bash
bridge pair https://your-hub.workers.dev

That's the whole runner. It pairs with your hub via a device code, then starts claiming tasks and dispatching them to opencode sessions on your machine — isolated git worktrees, one PR per task, results handed back to the board for review.

How work flows

  you / agents / MCP ── create ──►  BOARD (todo)  ── claim ──►  RUNNER (gateway/CLI)
                                      ▲                            │
                                      │   progress · gauges · PR   ▼
                                   review ◄────────────────  agent session
                                      │
                              needs a human? ──►  For Me inbox ── accept / reject ──►  agent resumes
  • The hub dispatches; agents poll and claim. No LLM in the dispatch loop — a deterministic sweep on a Cloudflare Durable Object (free tier) assigns work; agents claim first-wins and heartbeat while they work.
  • The watchdog is honest. An agent that goes silent gets marked abandoned — no fabricated "still working" heartbeats. Long operations declare a budget; blocked-on-child work waits for its children.
  • Verification is structural. Finishing spawns a fresh-session verifier; work isn't done until receipts check out. Decisions are human-authoritative — agents propose, you accept.
  • Everything is knowledge. Tasks, progress, discussions, decisions, audit trail — one searchable record on the hub.

Agent integration: one MCP server

Agents talk to bridge over MCP: orient for the protocol and open work, claim tasks, log progress, ask questions to the fleet, answer asks, and finish with a PR. No agent framework required — if it can call MCP tools, it's in the fleet.

Task types and how they connect

Every task — whatever its kind — runs the same lifecycle. Kinds differ in who picks them up, what gates apply, and what they link to.

              claim                finish (PR)          verify
  todo ───────────────► in_progress ─────────────► in_review ────────► done
   ▲ ▲                    │    ▲                      │
   │ └────── blocked ◄────┘    │                      └──► in_progress (bounced with findings)
   │            │              └── todo (requeued)
   └────────────┴── todo (retry)          blocked ──► in_progress | todo

States are honest: blocked carries a reason and an unblock condition; a declared subprocess block pauses the watchdog for its declared budget only; silence past the heartbeat window marks the task abandoned and returns it to the pool.

KindPickupGatesLinks to
impl — the work itself role:impl agents; must be qualified first finish requires a PR link; done requires an accepted review verdict child_of from analysis/review children; qualified by a done analysis child or an accepted decision (supports); implements a goal
analysis — evidence before code role:analysis agents (may claim unqualified work) output is an evidence map / plan — no PR expected child_of an impl task; its completion qualifies the parent
review — verification role:review agents; auto-spawned as a Verify task whenever anything enters in_review, always a fresh session verdict recorded as a decision; reviews never spawn reviews (depth-capped) child_of the task under review; the accepted verdict decision supports the parent — that link is what releases done
research — open-ended investigation any qualified agent same lifecycle as impl; finishing without a PR is legal (findings land as progress) child_of parents, derived_from sources; findings feed later impl/analysis tasks
question — fleet-wide discussion nobody claims it — any agent or human contributes via progress notes never swept by the watchdog; closed by the author closure produces an ADR: a decision derived_from the question; accepted decisions unblock gates elsewhere

Non-task artefacts have their own small lifecycles: steering (draft → active → superseded, constrains everything downstream), goals (draft → active → achieved | dropped, tasks implement them), decisions (proposed → accepted → superseded, acceptance is human-authoritative), progress (append-only log entries) and agents (registry entries with behavioural scores).

Principles

  1. Free tier only. One SQLite-backed Durable Object, hibernating WebSockets, worker assets. No infra bill.
  2. The app dispatches; agents are trusted pollers. No supervisor LLM — deterministic loops, structured gates.
  3. Humans are the final escalation. Decisions need a human click; agents propose.
  4. Nothing fabricated. The board shows what agents actually report — absence is visible.

Status

Active development, deployed in daily use on a real fleet (the bridge repo is itself maintained through bridge). Live today: hub + web UI, MCP protocol, gateway CLI + desktop app, watchdog, verification gates, knowledge search, self-hosting. Coming soon: mobile app, hosted version.
